## Promise to the person using the app

- A signed-in Table member can read its conversation and photos. A person outside the Table cannot. Tables are not end-to-end encrypted; a privileged database or Storage operator can access them.
- An account erasure request must immediately stop the account's app access and make that person's authored text, names, saved copies and media unavailable to other users. Structural conversation positions and independent replies from other people may remain as anonymous stubs.
- The app must not call the request complete until private Storage objects, the Auth identity and any derived previews have been removed and checked. Backups, logs, signed URLs and caches need a published retention statement before real-user invitations; the local prototype has no verified end-to-end purge guarantee for those systems.
- Ordinary Plate removal is a different action: it leaves frozen Menu reminders. Erasure overrides that retention.

## Inventory from the current schema

| Data | Where it lives | Erasure action |
| --- | --- | --- |
| Sign-in and name | `auth.users`, `private.profile_auth_links`, `profiles` | Disable app access first; clear name, unlink and remove Auth identity after content and objects are handled. Keep only a blank stable profile ID where foreign keys require it. |
| Authored Plates and their shares | `plates`, `plate_shares`, `timeline_entries`, `threads` | Blank authored Plate; blank this person's share introductions; preserve share/thread IDs and other people's independent replies. A share of the erased Plate loses its source content. |
| Table chat and replies | `timeline_entries`, `thread_replies` | Blank only rows authored by this person; clear author ID and request fingerprint. Keep positions and thread structure. |
| Formal Requests | `requests.question` plus Request root and thread | Clear the question and the authored root context; keep the root and independent answers. Current nonblank CHECK and immutable trigger must be explicitly revised. |
| Captured Plate saves | `menu_plate_saves`, `menu_plate_sources` | Blank every save of a Plate authored by this person, including saves owned by someone else. Their own Menu becomes inaccessible after account disable; any retained rows must be blank. Source relationships may remain as non-content IDs. |
| Live Request saves | `menu_request_saves` | Its content is looked up from the Request. Once the root is erased, the saved link may lead to an unavailable stub, without leaking the question. |
| Table names and ownership | `groups`, `group_memberships`, `membership_periods` | Close active membership and remove ownership. An available Table must still have an active owner **and** a non-null `created_by`; a continuing Table therefore needs a reviewed creator-attribution transfer. The owner chose to archive a Table if the erasing account is its sole owner. The proposed database representation is `groups.availability = 'erased'`, with blank name and creator: it revokes every member's access while preserving their independent replies as inaccessible structural records. The preflight must show the Table and number of other active members before that action. Historical membership IDs remain structural; exposed views must render erased profiles as “Former member”. |

| Table photos | `table_upload_intents`, `table_media_assets`, `entry_media`, `reply_media`, `table-staged-assets`, `table-media` | Revoke access to this person's attachments; remove staged and served objects. Other members' photos and replies remain. |
| Derived Menu previews | `menu_preview_jobs`, `menu_preview_assets`, `menu_plate_saves.preview_asset_id`, `menu-previews` | Trace by source Plate and by saver. Revoke read before deleting all affected preview objects, including jobs that finish during the request. |

## Required workflow and ordering

1. **Preflight, read only.** Resolve the caller from Auth on the server; count all affected records and Storage paths. Report Tables where the account is an owner, especially any that would lose their last active owner. Never accept a profile ID supplied by the browser for self-erasure.
2. **Lock and revoke.** In one database transaction, lock the profile first, then affected Tables in ID order, following the existing lock rules. Set profile to `disabled` so `private.current_profile_id()` stops authorising reads or writes. Handle ownership and membership consistently; close each open period with `end_reason = 'erased'`.
3. **Blank content.** In the same transaction, blank authored Plates, chat, Requests, replies, copied Menu saves and display name. Use a narrowly scoped security-definer operation, not broad client UPDATE grants. Revise immutable guards only for a transition to `erased` under that operation; ordinary edits stay forbidden. Mark affected media inaccessible before transaction commit. Record exact bucket/path pairs in a private cleanup queue. The queue itself must never be selectable by clients.
4. **Remove objects.** A local worker claims queued paths, removes private Storage objects idempotently, and records success or a retriable error. It must also cover staged uploads, unattached processed objects, derived previews and objects created by an in-flight worker. New promotion/completion attempts for a disabled uploader, erased source Plate or disabled saver must fail before becoming readable; any object uploaded before a failed completion must enter cleanup.
5. **Finish identity.** Once every object is verified absent, remove the private Auth link and set the blank profile to `erased` in one database transaction, then remove the now-unlinked local Auth user through the admin API. Keep a non-identifying completion marker and counts. Do not mark complete on a partial Storage/Auth failure; retry safely. The Auth user may temporarily remain without an app profile if its separate removal fails.
6. **Verify.** Check signed-in access is revoked, other-member Table reads show anonymous stubs, independent replies remain, no Menu snapshot or preview survives, all five buckets lack the account's affected objects, and retries do not restore content. Exercise a processing-worker race. Test with at least two accounts and a shared Table before real users.

## Existing schema changes needed

The current database deliberately prevents parts of this workflow. A migration would need focused changes to the `requests` question CHECK, the immutable guards on authored entries/replies/Menu saves, the no-delete trigger on private Auth links, and media completion functions. These changes are deliberate deletion/guard changes under `AGENTS.md`; preparation, local application and actual erasure must each be reviewed for their exact effects. Do not use a database reset as a shortcut.

The worker now registers served-object attempts before upload, removes objects after failed completion, and reconciles known queued paths plus staged/preview account prefixes during erasure. A finishing attempt requeues its path to cover an upload that completed after an early removal. Absence is checked using paginated Storage listing because the local server rejects the SDK's `exists` endpoint. Storage removal and Auth deletion remain outside the PostgreSQL transaction, so the durable queue and resumable completion are necessary. A crashed attempt remains pending until explicit recovery; it must never be treated as successful cleanup merely because time passed.

## Privacy findings beyond erasure

- The original `profiles_signed_in_read` policy permitted any active account to query the entire active profile directory, including names of people with no shared Table or Plate. With the owner's approval, `20261009000610_profile_visibility.sql` was applied locally on 2026-10-10: it now shows each account its own profile, authors of available Plates, and current peers in an available Table. The earlier read-only `00600` impact migration was separately approved and both migrations are recorded in the local CLI ledger. Applied-schema rollback-only tests passed those paths and unrelated-account denial.
- Plate, Table and Menu image links currently expire after one hour. Revoking a database read policy does not itself revoke a previously issued signed URL. Object removal is therefore part of the immediate erasure path, and the completion check must try previously issued URLs as well as new requests. Cache behaviour needs verification in the chosen hosting environment.
- The local worker holds a service-role key in its own process and can read private source images. Keep it isolated from browser code, and do not present Table content as end-to-end encrypted.

## Release gate

Before inviting real people: implement and test the full flow, write an honest user-facing retention statement for database backups, Storage backups, logs, signed URLs and caches, choose retention periods, and obtain a privacy/legal review appropriate to the product and hosting region. Until then, do not show an “account erased” confirmation or claim permanent deletion.
