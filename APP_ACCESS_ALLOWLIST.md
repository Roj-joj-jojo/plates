## Everyday use

An Alpha **Live accounts** section is now enabled locally beneath the pending list. It uses the same appointed-owner authority, with email/name, separate last-active and last-sign-in timestamps, owner protection and an exact-email deletion confirmation with impact preview. Activity is a private server timestamp recorded at most once a minute during recent foreground use; older accounts show “Not recorded yet.” It records no device/IP/event history and is cleared at erasure cutoff.

Migration `20261011000200_admin_account_management.sql` is applied locally with specific owner approval, and `APP_ADMIN_ACCOUNT_ERASURE_ENABLED=true` is configured. General self-service deletion remains disabled. The trusted local action verifies the signed-in owner, writes the independent intent before cutoff, then starts only the selected profile’s worker. The worker claims only that profile’s objects and stops on completion, error or 15 minutes; unfinished uploads may require separately reviewed recovery. Pending rows offer Retry cleanup and refresh progress. Hosted execution requires future hosting/worker integration. Activation started no worker and deleted no account/photo.

Verification update: the owner-authorised candidate and installed-schema rollback SQL, synthetic admin coordinator, existing record coordinator regression, lint, typecheck, Node syntax and Webpack build passed. Fixed the list’s email return type and an invalid synthetic test bucket. Browser/actual detached worker acceptance is still untested. Actual accounts are erased only after the exact target is reviewed and confirmed.

After setup, the owner opens **Account → Manage app access**, adds an email address and shares the normal Plates address themselves. Adding an address sends no message. Only the appointed active owner can read pending addresses or add/withdraw/reallow permission; Table Admin rights do not confer this authority.

The approved person creates an account using that address and the existing email-code flow. A database trigger on Auth account creation enforces the allowlist even when someone bypasses the app UI. Permission is consumed atomically with signup. Failed signup rolls consumption back, so the person can retry. The pending address disappears after account creation; duplicate email storage is cleared, leaving a private Auth reference until the established erasure cutoff clears it.

**Withdraw** disables an unused permission, with a confirmation identifying its exact email. **Allow again** reinstates it. Neither operation deletes a row/account or removes Table membership. Existing accounts are intentionally preserved and can continue signing in. Already-created accounts cannot be added to the pending list. The list governs new account creation, not ongoing suspension; account suspension is a separate, unimplemented control.

Addresses are trimmed and lowercased, without stripping Gmail dots or plus suffixes. No public directory/search exposes the list. The public status RPC reports only whether restrictions are enabled and whether the current caller is the appointed owner.
